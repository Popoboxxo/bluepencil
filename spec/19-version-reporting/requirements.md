## FR-19.1 The same version answers "which build is this" everywhere: the element carries data-bp-v…

```attr
prio: P1
origin: N
milestone: "M5"
status: approved
verify: Test
version: 1

```

The same version answers "which build is this" everywhere: the element carries data-bp-version and a static version; the layer settings show a static bluepencil <VERSION> line; window.bluepencilAttach.version and the attach-version attribute report the mounted build; the hub reports it in GET {base}/health and --version; the CLI reports it in bluepencil --version; the MCP server reports it in the initialize handshake. A run straight from the sources reports dev

*Acceptance criteria:* In a build, every listed surface reports the same string; a source run reports `dev`; the element sets `data-bp-version` on connect; no bare semantic-version literal exists outside the single version module

## FR-19.2 The loader reports the version it actually mounted: with a manifest it reports the manif…

The loader reports the version it actually mounted: with a manifest it reports the manifest version, otherwise the version of the build it loaded; it emits that value in bp-attach-ready and bp-attach-updated and on the mounted element's attach-version attribute. unknown is reserved for the case where the version genuinely cannot be known

*Acceptance criteria:* With a manifest, `window.bluepencilAttach.version` and the event detail equal the manifest version; without one, they equal the loaded build's version; the `attach-version` attribute and the event detail agree with the handle
