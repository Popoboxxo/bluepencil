## FR-3 Note model

| ID | Requirement | Prio | Ms | Origin | Acceptance criteria |
|---|---|---|---|---|---|
| FR-3.1 | A note has: `id`, `created_at`, author (+`author_type`), `type`, `intent`, `status`, `body`, `quote`, `anchor`, `context`, `route`, `session_ref` | P0 | M1 | P | All fields present in the JSON export and validated |
| FR-3.2 | `type` ∈ {`text`, `design`, `bug`, `feature`}; `intent` ∈ {`implement`, `feedback`}; `status` ∈ {`open`, `done`, `needs_decision`} | P0 | M1 | P | Invalid values rejected by the API/adapter |
| FR-3.3 | Notes carry an append-only **thread** of messages with `author_type` (`human`/`agent`) and `kind` (`note`/`decision_request`/`decision`/`feedback`/`reply`) | P0 | M1 | P | Agent and human replies appear in order, each with author and timestamp |
| FR-3.4 | Notes can be grouped into a **session** and exported/purged per session | P1 | M2 | G | Purge removes exactly the session's notes, count reported |
| FR-3.5 | The schema is versioned and documented; migrations from older data are defined | P0 | M1 | G | A v1 file loads in a v2 build; migration is documented and tested |
| FR-3.6 | An **optional** `severity` ∈ {`blocker`, `major`, `minor`} may be set on a note; it is orthogonal to `type`/`intent`, meaningful only for `type` = `bug`, and omitted otherwise | P1 | M2 | G | A note without `severity` stays valid (old stores/bundles import unchanged, no `schemaVersion` bump); an unknown `severity` on import degrades safely (dropped, treated as absent), mirroring the unknown-`type`→`text` fallback |
| FR-3.7 | An **optional** `priority` ∈ {`high`, `medium`, `low`} may be set on a note; it is orthogonal to `type`/`intent`, meaningful only for `type` = `feature`, and omitted otherwise. It is an additive change without a `schemaVersion` bump: an older reader degrades `feature` to `text` and drops `priority`, a newer reader imports old data unchanged, and an unknown priority on import is dropped (treated as absent) | P1 | M2 | G | A note without `priority` stays valid; `priority` on a non-feature note is rejected by validation and dropped by coercion/migration; old stores and bundles import unchanged without a schema bump; an unknown value degrades to absent |

> **Field names as implemented:** the note JSON uses camelCase — `createdAt`, `updatedAt`,
> `authorType`, `sessionRef`, `schemaVersion`, `messages` (the thread) — and `quote` / `route` sit on
> the anchor (`anchor.quote`, `anchor.route`); `context` is `null` for text notes. Names are declared in
> `src/core/model.ts`, so every acceptance criterion above is checked by literal key name in the
> exported JSON.

## FR-17 Attach loader — one script tag, no host build step

A host adds bluepencil by loading one script, without a build step of its own. The loader defines
the `<bluepencil-notes>` element, mounts it, and exposes a small API for runtime updates. This
section documents the behaviour that ships today; it adds no feature.

| ID | Requirement | Prio | Ms | Origin | Acceptance criteria |
|---|---|---|---|---|---|
| FR-17.1 | **One tag attaches with the documented defaults**: a `<script src="attach.js">` with no `data-*` attribute at all defines the element and, with `data-auto` at its default `true`, mounts exactly one `<bluepencil-notes>` on `document.body`; `data-auto="false"` defines the element and mounts nothing. `window.bluepencilAttach` exposes `version`, `src`, `instances`, `destroy()`, `reload()` and `check()`, plus `handles` and `attach(options)` for the per-script and programmatic view | P0 | M3 | G | A page with one bare loader script ends with exactly one mounted element and a populated `window.bluepencilAttach`; `data-auto="false"` yields zero mounted elements but a defined tag; a tag added after `DOMContentLoaded` is picked up by `check()`; `destroy()` removes every mounted element and the layer |
| FR-17.2 | **One attribute vocabulary for element and loader**: every element attribute has a `data-*` mirror on the loader, and only non-empty loader values are forwarded (so `data-modes` without a value is not forwarded). ## FR-18 Store journal — who changed which note, when

The hub keeps a history of every accepted mutation. History is a convenience, not a precondition for
serving notes: a journal failure never fails a request. This section documents the behaviour that
ships today; it adds no feature.

| ID | Requirement | Prio | Ms | Origin | Acceptance criteria |
|---|---|---|---|---|---|
| FR-18.1 | **Every accepted mutation is recorded**: `create`, `update`, `message`, `bulk-delete` and `import` produce an entry with operation, note ID (when there is one), actor (when known), summary, sequence number and timestamp. `--journal auto` (the default) chooses `git` when the store lives inside a git work tree and `file` otherwise; `--journal none` disables history on purpose. A requested backend that cannot be provided degrades to `none` **with a reported reason**, never silently | P1 | M5 | N | Each of the five operations yields one entry with `op`, `noteId` (where applicable), `actor` (where known), `summary`, `seq` and `ts`; `auto` selects `git` inside a work tree and `file` outside one; `--journal git` outside a work tree reports `none` plus a reason on `stderr` and in the status instead of doing nothing |
| FR-18.2 | **Auditable, replayable history**: the file backend is append-only and hash-chained (each entry hashes the previous one), so tampering is detectable; `GET {base}/journal` returns `{journal: {backend, location, entries, lastSeq}, entries}` and accepts `?since=<seq>` to return only newer entries, oldest first. The journal route is `GET`-only and answers `405` to `OPTIONS` | P1 | M5 | N | The file backend writes one line per mutation with `prevHash`/`hash`; a modified line breaks verification; `?since=1` does not repeat entry 1; the response carries the status object and the entries; `OPTIONS` on the journal route answers `405` |
| FR-18.3 | **Journal failures never roll back a note, and the git backend is path-limited**: the note is persisted before the journal is written; a failure is reported once on `stderr` and stays visible in the status and in `GET {base}/journal`. The git backend stages and commits only the configured store and mirror paths, coalesces mutations over `--journal-coalesce` ms (default 2000) into one commit, and takes its identity from `--journal-author` or `BLUEPENCIL_JOURNAL_AUTHOR` (flag wins). The public journal keeps `location` and `author`; that is the accepted risk documented in FR-6.7 | P1 | M5 | N | A failing journal runner still lets the note write succeed and reports the failure once; two mutations inside the window produce one commit that touches only the configured paths; a pre-staged foreign change stays out of the notes commit; `journal.author` reports the configured identity, or the repository identity when none is configured |

## FR-20 Presentation mode — speaker notes, cue plan, audience view

A layer on top of the annotation layer, not a second data layer: a speaker note is an ordinary note

behaviour that ships today; it adds no feature.

| ID | Requirement | Prio | Ms | Origin | Acceptance criteria |
|---|---|---|---|---|---|
| FR-20.1 | **Three states, and `off` is not a variant of `read`**: `off` leaves the layer and the host page untouched; `read` shows the presenter panel without a write path; `edit` shows the same panel with the two write paths. One gesture toggles `off` and `read`. An audience tab is read-only by construction and never gets a write path. Teardown removes the panel, the timer and the channel, and is idempotent (FR-12.2, NFR-15) | P1 | M5 | N | With the mode `off` no panel, timer or channel exists; toggling opens the panel in `read` and closes it again; an audience tab has no write path; `destroy()` and `disable()` leave no panel, timer, listener or channel behind and can be repeated |
| FR-20.2 | **One store, no second truth**: the mode reads the note set from the layer's own store, so a speaker note is the same note the review list and the export show; a write from the panel goes through the layer's normal mutation path, and a store change refreshes the panel. ## Revised for 0.15.0 — viewer launcher entry points (Issue #144)

**FR-6.17** named exactly one operator entry point: `{base}/viewer/start?k=` plus the
`x-bluepencil-admin` header. For a browser that is the wrong instrument — a secret typed into a URL
lands in the address bar, in history, in the `Referer` of the next hop and in every proxy log. The
requirement is therefore widened to three equivalent paths: a form POST with the secret in the body
(FR-6.26, FR-6.27), the header, and `?k=` for scripts. FR-6.21 now states where the secret may
travel and names the retained `?k=` path as an explicit, documented exception to "never in a URL"
(backwards compatibility for scripts; decision of the requester — `?k=` is not deprecated).
This is a conscious departure from "no POST form"; the existing `?k=` GET path stays and is
not deprecated. Everything else in FR-6.17 is unchanged: the viewer still runs on its own origin,
the hub port still answers `404` for viewer content, and no content is served before
`viewer.origin` is resolved. New requirements: FR-6.26–FR-6.30; the viewer origin is reported on
the authenticated `/admin/status` (FR-6.29), deliberately **not** on the credential-free `/config`.
